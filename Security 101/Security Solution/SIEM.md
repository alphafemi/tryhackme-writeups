# SIEM Fundamentals


---

**Security Information and Event Management (SIEM)** is the core security solution used by SOC analysts to collect, normalize, correlate, and analyze logs from across a network — turning scattered raw data into actionable detections.

---

### Log Sources

Every device in a network continuously generates logs — these devices are called **log sources**, and they fall into two categories:

| Category | Generated By | Example Events |
|---|---|---|
| **Host-Centric** | Windows, Linux, servers, endpoints | File access, authentication attempts, process execution, registry key changes, PowerShell execution |
| **Network-Centric** | Firewalls, IDS/IPS, routers | SSH connections, FTP file access, web traffic, VPN access, network file sharing |

---

### Why Raw Logs Alone Aren't Enough

| Challenge | Description |
|---|---|
| **Numerous Log Sources** | Hundreds of events per second, scattered across many devices — manually checking each one is tedious. |
| **No Centralization** | Logs live on the machines that generated them; analyzing them means connecting to each source individually (SSH, RDP, etc.). |
| **Limited Context** | A single log rarely tells the full story — e.g., a "normal" file access event may actually be part of lateral movement after a separate compromise. |
| **Limited Analysis** | The sheer volume of logs makes manual, human-only analysis unrealistic — important events get missed. |
| **Format Issues** | Different sources produce logs in different formats, making cross-source analysis difficult without standardization. |

SIEM exists specifically to solve these problems.

---

### Core Features of a SIEM

| Feature | What It Does |
|---|---|
| **Centralized Log Collection** | Pulls logs from all sources (endpoints, servers, firewalls, etc.) via lightweight agents or APIs into one place — no more jumping between machines. |
| **Normalization** | Breaks raw logs into fields (**parsing**) and converts logs from different sources into one consistent format (**normalization**). |
| **Correlation** | Links logs from different sources to reveal patterns invisible in any single log — e.g., a new-IP VPN login + document access + PowerShell execution + outbound connection together may indicate data exfiltration, even though each event looks harmless alone. |
| **Real-time Alerting** | Triggers alerts when built-in or custom detection rules are satisfied, notifying analysts for investigation. |
| **Dashboards & Reporting** | Presents normalized data as actionable insights — alert highlights, system notifications, failed login lists, events ingested, rules triggered, top domains visited, etc. |

> Additional SIEM capabilities beyond this scope include threat intelligence feed integration, extensive data retention, and powerful search capabilities.

### Example Log Sources in Practice

#### Windows
Windows logs every event with a unique Event ID, viewable via **Event Viewer**. These logs are forwarded from every endpoint to the SIEM for centralized monitoring.

#### Linux
Common log locations:

| Path | Contents |
|---|---|
| `/var/log/httpd` | HTTP request/response and error logs |
| `/var/log/cron` | Cron job events |
| `/var/log/auth.log` / `/var/log/secure` | Authentication logs |
| `/var/log/kern` | Kernel-related events |

### Log Ingestion Methods

| Method | Description |
|---|---|
| **Agent / Forwarder** | Lightweight software installed on the endpoint that captures and sends logs to the SIEM server (e.g., Splunk's "forwarder"). |
| **Syslog** | Standard protocol for collecting data from systems (web servers, databases, etc.) and streaming it in real time to a central destination. |
| **Manual Upload** | Offline data ingestion for quick, ad-hoc analysis (supported by tools like Splunk, ELK). |
| **Port Forwarding** | SIEM listens on a configured port; endpoints forward data directly to that port. |

### Detection Rules

Detection rules are logical expressions that trigger alerts when their conditions are met. Since they key off specific fields, **normalized logs are essential** for rules to work reliably.

**Example rules:**

- 5 failed login attempts within 10 seconds → *Multiple Failed Login Attempts* alert
- Successful login immediately after multiple failures → *Successful Login After Multiple Attempts* alert
- Any USB insertion → alert (useful where USB use is restricted)
- Outbound traffic exceeding a threshold (e.g., 25 MB) → *Potential Data Exfiltration* alert

**Rule construction — Use Case 1 (log clearing):**

> Adversaries often clear event logs to cover their tracks. Event ID `104` marks a log-clear attempt.
>
> **Rule:** `IF LogSource = WinEventLog AND EventID = 104 → Alert: Event Log Cleared`

**Rule construction — Use Case 2 (recon command execution):**

> Adversaries often run `whoami` post-exploitation. Key fields: log source, Event ID `4688` (process execution), and the `NewProcessName` field.
>
> **Rule:** `IF LogSource = WinEventLog AND EventCode = 4688 AND NewProcessName CONTAINS "whoami" → Alert: WHOAMI Command Execution Detected`

---

### Alert Investigation Workflow

Analysts spend most of their time in SIEM dashboards, which summarize key network activity. When an alert fires:

1. Examine the events/flows tied to the alert
2. Check which rule conditions were satisfied
3. Determine **True Positive** vs. **False Positive**

| Outcome | Next Steps |
|---|---|
| **False Positive** | Tune the rule to prevent recurrence. |
| **True Positive** | Investigate further; contact the asset owner; if confirmed malicious, isolate the infected host and block the suspicious IP. |

### SIEM Quick Reference

| Concept | Summary |
|---|---|
| SIEM does | Collect → Normalize → Correlate → Detect → Alert |
| Log source categories | Host-centric, Network-centric |
| Raw log problems solved | Volume, no centralization, limited context, limited analysis, format inconsistency |
| Core features | Centralized Collection, Normalization, Correlation, Real-time Alerting, Dashboards |
| Ingestion methods | Agent/Forwarder, Syslog, Manual Upload, Port Forwarding |
| Key Windows Event IDs | 104 (log cleared), 4688 (process execution) |
| Alert triage outcomes | False Positive (tune rule) vs. True Positive (investigate & contain) |

## Summary

- A **SIEM** centralizes log collection from **host-centric** (Windows, Linux, endpoints) and **network-centric** (firewalls, IDS/IPS, routers) sources, solving the problems of volume, decentralization, limited context, limited manual analysis, and inconsistent log formats.
- Its five core features are **centralized collection, normalization** (parsing raw logs into consistent fields), **correlation** (linking events across sources to reveal patterns), **real-time alerting**, and **dashboards/reporting**.
- Logs reach the SIEM via an **agent/forwarder**, **syslog**, **manual upload**, or **port forwarding**.
- **Detection rules** are logical expressions built on normalized fields (e.g., Windows Event ID `104` for log clearing, or `4688` combined with a process name for command execution) that trigger alerts when satisfied.
- When an alert fires, analysts examine the underlying events, confirm which rule conditions matched, and classify the result as a **false positive** (tune the rule) or a **true positive** (investigate, contain, and escalate).
