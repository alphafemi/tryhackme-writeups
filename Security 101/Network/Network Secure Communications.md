TLS, SSH, SFTP & VPNs — Secure Communications

### The Problem: Cleartext Protocols

Historically, protocols like HTTP, FTP, SMTP, POP3, and IMAP sent all data — including usernames, passwords, and message content — as **plain text**. Any attacker with network access who set their NIC to **promiscuous mode** (capturing all packets, not just those addressed to them) could read credentials from captured traffic without any special tools.

Modern networks have largely eliminated this vulnerability through encryption.

### TLS — Transport Layer Security

**TLS** (Transport Layer Security) is the cryptographic protocol that secures the majority of internet communication today. It ensures:

| Property | Meaning |
|---|---|
| **Confidentiality** | Data is encrypted — unreadable by anyone intercepting the traffic |
| **Integrity** | Data cannot be modified in transit without detection |

#### Brief History

| Year | Milestone |
|---|---|
| 1995 | Netscape releases **SSL 2.0** — first public secure web protocol |
| 1999 | IETF releases **TLS 1.0** — upgraded successor to SSL 3.0 |
| 2018 | **TLS 1.3** released — major overhaul; current standard |

> The terms SSL and TLS are often used interchangeably in practice, though SSL is deprecated — all modern systems use TLS. When you see "SSL certificate," it typically means a TLS certificate.

#### How TLS Works

TLS operates at the **transport layer** — it wraps any application-layer protocol without requiring changes to TCP/IP or the application protocol itself.

**Three-step connection for HTTPS:**
```
1. TCP three-way handshake (SYN → SYN-ACK → ACK)
2. TLS handshake — negotiate cipher suite, exchange certificates, establish session keys
3. Encrypted application data (HTTP, SMTP, etc.) — transmitted as "Application Data"
```

> Once TLS is established, a packet sniffer like Wireshark sees only **"Application Data"** — the protocol type and content are hidden. Without the session's private key, captured traffic appears as gibberish.

#### TLS Certificates

| Concept | Description |
|---|---|
| **CSR** (Certificate Signing Request) | Generated by the server admin; submitted to a CA for signing |
| **CA** (Certificate Authority) | Trusted third party that verifies and signs certificates |
| **Signed certificate** | Proves the server's authenticity — browsers verify the CA's signature |
| **Self-signed certificate** | Signed by the server itself — cannot prove authenticity to clients |
| **Trusted CAs** | Pre-installed in browsers and OSes; their signatures are trusted by default |

> **Let's Encrypt** provides free, automated, CA-signed certificates — removing the cost barrier to HTTPS adoption.

### Secure Protocol Variants

Adding TLS to an existing protocol is straightforward — the protocol operates identically, just wrapped in encryption. The convention is appending **"S"** (for Secure) to the protocol name.

#### Port Number Comparison: Insecure vs. Secure

| Protocol | Insecure Port | Secure (TLS) Version | Secure Port |
|---|---|---|---|
| HTTP | 80 | **HTTPS** | 443 |
| SMTP | 25 | **SMTPS** | 465 / 587 |
| POP3 | 110 | **POP3S** | 995 |
| IMAP | 143 | **IMAPS** | 993 |
| FTP | 21 | **FTPS** | 990 |
| DNS | 53 (UDP) | **DoT** (DNS over TLS) | 853 |

#### HTTP vs. HTTPS — Connection Flow Comparison

```
HTTP:
  TCP Handshake (3 packets)
  → HTTP Request/Response
  → TCP Termination

HTTPS:
  TCP Handshake (3 packets)
  → TLS Handshake (multiple packets — negotiate, exchange certs, derive keys)
  → Encrypted HTTP (shown as "Application Data" in packet captures)
  → TCP Termination
```

> From a Wireshark packet capture perspective: HTTP traffic is readable as plain text; HTTPS shows only "Application Data" — the contents require the session's private key to decrypt.

### SSH — Secure Shell

**SSH** (Secure Shell) replaced Telnet as the standard for secure remote administration. Developed by Tatu Ylönen and released in 1995 (the same year as SSL 2.0), it provides an encrypted replacement for cleartext remote terminal access.

**Port:** TCP 22

#### Why SSH over Telnet?

| Feature | Telnet | SSH |
|---|---|---|
| Encryption | None — cleartext | Full end-to-end encryption |
| Authentication | Password only | Password, public-key, or two-factor |
| Integrity protection | None | Cryptographic integrity verification |
| MITM protection | None | Alerts on changed server keys |
| Tunneling | No | Yes — can route other protocols through SSH |
| X11 forwarding | No | Yes — run remote GUI applications locally |

#### Connecting via SSH

```bash
ssh username@hostname       # connect as specified user
ssh hostname                # connect as current local username
ssh 192.168.124.148 -X     # -X enables X11 forwarding (graphical apps)
```

> On first connection, SSH presents the server's fingerprint — verify it before accepting. Future connections will warn if the key changes, alerting you to potential MITM attacks.

#### How SSH Compares to Telnet in Wireshark

- **Telnet:** all traffic visible as plain text — credentials, commands, and output fully readable
- **SSH:** all traffic encrypted — only handshake metadata visible; session content is opaque

### SFTP — SSH File Transfer Protocol

**SFTP** is a secure file transfer mechanism built into the SSH protocol suite — it is **not** FTP with TLS. It runs entirely over the SSH connection.

| Property | Detail |
|---|---|
| Port | **22** (shared with SSH) |
| Security | SSH encryption (not TLS) |
| Enabling | Configured in the OpenSSH server settings |

```bash
sftp username@hostname    # connect to SFTP server
get filename              # download a file
put filename              # upload a file
```

> SFTP commands are **Unix-like** and differ from FTP commands (e.g., `get`/`put` are the same, but directory navigation and listing syntax differs slightly).

#### SFTP vs. FTPS

| | SFTP | FTPS |
|---|---|---|
| Based on | SSH | FTP + TLS |
| Port | 22 | 990 |
| Certificate required | No | Yes (TLS certificate) |
| Firewall-friendliness | Single port — straightforward | Dual connections — can be complex |
| Setup complexity | Enable one option in OpenSSH | Requires TLS certificate configuration |

> **SFTP** is generally the simpler and more secure choice for new setups. **FTPS** exists primarily for compatibility with legacy FTP infrastructure.

### VPN — Virtual Private Network

A VPN creates an **encrypted tunnel** between two endpoints over an untrusted network (typically the internet), allowing devices to communicate as if on the same private network regardless of physical location.

#### Use Cases

| Scenario | Description |
|---|---|
| **Site-to-site** | Connect multiple office branches to a central main branch — all traffic between offices travels encrypted through the VPN tunnel |
| **Remote user** | Individual devices connect to a company VPN server — accesses internal resources as if physically on-site |
| **Privacy/anonymity** | All internet traffic routed through the VPN server — remote servers see the VPN server's IP, not the user's real IP |
| **Geo-bypass** | Traffic appears to originate from the VPN server's country — circumvents geographic content restrictions |

#### How a VPN Tunnel Works

```
[Remote Branch / User]
        │
        │  Encrypted VPN tunnel
        │  (ISP sees only encrypted traffic)
        ▼
[VPN Server / Main Branch]
        │
        │  Decrypted internal traffic
        ▼
[Internal Resources]
```

> The ISP sees only **encrypted, opaque traffic** flowing to the VPN server — it cannot read the content or inspect the actual destination of the traffic within the tunnel.

#### Key Properties and Limitations

| Property | Detail |
|---|---|
| **Confidentiality** | Traffic is encrypted — ISP and intermediaries cannot read it |
| **IP masking** | Internet services see the VPN server's IP, not the user's real IP |
| **Not always all-traffic** | Some VPN configurations provide network access without routing all traffic through the tunnel — verify based on use case |
| **DNS leaks** | Some VPN configurations may leak DNS queries to the local ISP despite the tunnel — test explicitly if privacy is the goal |
| **Legal considerations** | VPN use is restricted or illegal in some countries — check local regulations before use, especially when traveling |
