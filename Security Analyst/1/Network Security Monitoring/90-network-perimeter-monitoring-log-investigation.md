# Network Perimeter Monitoring & Log Investigation

## Overview

This document covers monitoring the network perimeter and investigating its logs: the core components of a network and why each matters for security, the principle of network visibility, host-centric vs. network-centric log sources, the perimeter and its components, three monitoring scenarios (port scanning, web attacks, VPN brute-force) with pattern-recognition takeaways, and a worked five-stage attack chain investigation using command-line log analysis.

---

Networks are the backbone of every modern organization — servers, workstations, applications, and security devices are all interconnected into a single ecosystem. The **network perimeter** is where this internal ecosystem is segregated from the external Internet, and it's often the first target for attackers.

---

### Network Components — Building Blocks of a Network

Understanding what each device does and why it matters helps quickly identify suspicious activity.

| Component | Role | Security Importance |
|---|---|---|
| **User Workstations (Endpoints)** | Where employees do daily work (PCs, laptops) | Most common entry point for attackers (phishing, malicious downloads); less monitored, but compromise here enables lateral movement. Endpoint logs reveal malicious processes; network logs may first show C2 connections. |
| **File & Database Servers** | Store the business's most important asset — data | Prime targets for ransomware (maximizing impact) and data exfiltration campaigns |
| **Application Servers (Web, Email, VPN)** | Provide daily-use services to employees/customers | Externally facing → high-value targets; attackers constantly scan for vulnerabilities/misconfigurations as a foothold |
| **Active Directory (AD) / Authentication Servers** | The identity backbone — manages users, groups, computers, access rights | Controls all accounts/systems; targeted for privilege escalation, persistence, lateral movement — one compromised domain admin account can bring down the entire enterprise |
| **Routers & Switches** | Connect networks (routers) and devices within a network (switches) — the "circulatory system" | If compromised: MITM traffic interception, backdoors via rerouting, hidden channels to the internet |
| **Firewalls / Perimeter Devices** | Primary security gateway filtering traffic between trusted internal and untrusted external networks | Protects against direct internet exposure; logs are often the earliest indicator of port scans, brute-force, or exploitation attempts |

---

### Network Visibility

**Network visibility** is the ability to monitor and understand what's happening across a network — the core principle being *"you can't defend what you can't see."* It enables threat detection, incident investigation, and a strong security posture.

**What visibility enables:**

| Capability | Description |
|---|---|
| **Detect Anomalies** | Spot unusual patterns indicating an attack |
| **Investigate Incidents** | Piece together attack events to understand what happened |
| **Hunt for Threats** | Proactively search for hidden adversaries |
| **Ensure Compliance** | Meet regulatory logging/monitoring requirements |

Visibility comes from two primary log source categories — understanding their difference is key to building an accurate attack timeline.

---

### Host-Centric Logs

Generated by individual devices (hosts) — servers, workstations, laptops — giving a detailed, ground-level view of what's happening on a specific machine.

| Source | Examples |
|---|---|
| **Operating System Logs** | Windows Event Logs, Linux syslog, macOS logs — logons, process creation, service startups, failed logins |
| **Application Logs** | Web servers (Apache, Nginx), databases (MySQL, MSSQL), other software |
| **Security Tool Logs** | Antivirus, EDR agents, host-based IDS (HIDS) |

**What they answer:**
- Detailed forensic analysis (files accessed/modified/deleted)
- Process and execution tracking (malicious processes, unauthorized PowerShell, service changes)
- User activity monitoring (logons, privilege use — external attacks and insider threats)
- Malware impact assessment (registry/file system/service changes)

---

### Network-Centric Logs

Generated by network appliances monitoring traffic flowing *between* devices — the crucial "when," "where," and "how" of an attack.

**What they show:** Source/destination IPs, ports, protocols, and the action taken (allowed/blocked).

> **Analogy:** Host-centric logs tell you what happened *inside a room*; network-centric logs tell you *who entered and left the building*. A complete picture requires correlating both.

| Source | What It Provides |
|---|---|
| **Firewalls** | Every connection allowed/denied per security rules — first place to check for unauthorized attempts |
| **IDS/IPS** | Traffic matching known attack signatures or anomalous behavior — critical for real-time active-attack detection |
| **Routers/Switches** | Flow data summarizing conversations (who talked to whom, duration, data volume) — high-level overview |
| **Web Proxies** | Every website visited by users — web threats, policy violations, exfiltration attempts |
| **VPN** | Who's connecting remotely, from where, and when |

**Why they matter:**
- Early threat detection (blocking scans, brute-force, known-malicious IPs at the edge)
- Identifying C2 communication patterns
- Tracking lateral movement between compromised machines
- Detecting data exfiltration (unusually large/suspicious outbound transfers)
- Providing broad context on an attack's scope

### The Network Perimeter

The **perimeter** is the boundary separating the internal (trusted) network from the external (untrusted) Internet — the controlled entry/exit point for all traffic, and the organization's first and most critical line of defense.

#### Perimeter Components

| Component | Role |
|---|---|
| **Firewalls** | Filter traffic between internal/external networks |
| **Routers/Gateways** | Route traffic and enforce access rules |
| **DMZ (Demilitarized Zone)** | Buffer segment hosting public-facing servers (web, mail, VPN) |
| **Remote Access Gateways / VPNs** | Secure entry points for remote employees |

#### Why the Perimeter Matters

Attackers always start probing from outside — the perimeter is usually where SOC analysts first see malicious activity. A weak/misconfigured perimeter allows:

- Exploitation of exposed services (RDP, MySQL, SMB)
- Scanning and reconnaissance to map the network
- Brute-force attacks against login services
- Data exfiltration channels

#### Role of a Security Analyst

- Review firewall logs for blocked/allowed connections
- Identify scanning attempts or brute-force login attempts
- Flag unusual outbound traffic (malware beaconing, exfiltration)
- Understand what should/shouldn't be exposed at the perimeter

### Monitoring the Perimeter — Scenarios in Action

#### Scenario 1: Port Scanning

**Firewall Log pattern:** The same external IP repeatedly connecting to multiple ports on one internal machine in quick succession (e.g., ports 21, 22, 23, 25, 53 all `BLOCK`ed from one source).

**Verdict:** Classic port scan — the attacker is hunting for an open service to target.

#### Scenario 2: Web Attack (SQL Injection / XSS / Directory Traversal)

**WAF Log pattern:** A mix of ALLOW/BLOCK actions — filtering for `action=BLOCK` immediately surfaces threats, with the WAF explicitly naming the `attack_type` (SQL Injection, XSS, Directory Traversal).

**Verdict:** High-confidence alert — the WAF is actively identifying and blocking multiple web attack types from a single suspicious IP.

#### Scenario 3: VPN Brute-Force

**VPN Gateway Log pattern:** A flood of `FAILED_AUTH` events against common usernames (`admin`, `root`, `guest`, `user`) from one IP, with occasional legitimate `SUCCESS_AUTH` entries from different, unrelated IPs mixed in.

**Verdict:** Filtering/grouping by source IP reveals one IP responsible for hundreds of failed attempts — a credential-stuffing/brute-force attack, distinct from the scattered benign employee logins.

#### Key Pattern-Recognition Takeaways

| Pattern | Likely Meaning |
|---|---|
| One source → many destinations (ports/hosts) | Scanning |
| One source → one destination, repeated | Brute-forcing |
| Traffic at perfectly regular intervals | Malware beaconing |
| IDS alert naming *why* it fired | More valuable than a plain firewall block — context is key |

### Worked Incident: Full Attack Chain Investigation

**Scenario:** A SOC analyst reviews a month of perimeter logs (`firewall.log`, `ids_alerts.log`, `vpn_auth.log`) to reconstruct what an adversary did and whether they breached the perimeter.

#### Stage 1 — Reconnaissance

```bash
cat firewall.log | grep "BLOCK" | cut -d' ' -f5 | cut -d: -f1 | sort -nr | uniq -c
```

Counting blocked-request source IPs reveals one IP responsible for the most BLOCKs — the top recon suspect, used to pivot into further analysis.

```bash
cat firewall.log | grep <suspicious_IP> | grep "ALLOW"
```

Checking whether the firewall later *allowed* traffic from that same IP (to ports like 22, 445, 3389, 4444) confirms the attacker eventually gained access through exploitation.

#### Stage 2 — VPN Brute-Force / Credential Access

```bash
cat vpn_auth.log | grep FAIL | cut -d' ' -f3 | sort -nr | uniq -c
```

Identifies which source IP generated the most failed VPN logins.

```bash
cat vpn_auth.log | grep <suspicious_IP>
```

Reveals a rapid burst of `FAIL` attempts against a specific service account, followed by a `SUCCESS` and an assigned internal IP — confirming the attacker brute-forced valid credentials and pivoted into the internal network.

#### Stage 3 — Lateral Movement

```bash
cat firewall.log | grep <compromised_internal_IP> | grep "ALLOW" | head
```

Shows the compromised host probing other internal machines on SMB/RDP/SSH (445/3389/22).

```bash
cat ids_alerts.log | grep <compromised_internal_IP> | head
```

Surfaces matching IDS alerts: *"ET SCAN Possible SSH Scan,"* *"ET EXPLOIT Possible MS-SMB Lateral Movement,"* *"ET EXPLOIT Possible RDP Brute Force"* — confirming the host is actively exploiting internal services to move laterally.

#### Stage 4 — C2 Beaconing

```bash
cat ids_alerts.log | grep C2 | head
```

Surfaces repeated *"ET TROJAN Possible C2 Beaconing"* alerts between an internal host and a specific external IP/port (e.g., `:4444`) — direct evidence of an established C2 channel.

```bash
cat ids_alerts.log | grep -n <compromised_IP> | cut -d' ' -f6,7,8,9,10,19,22,23 | uniq -c | sort -nr | head
```

Aggregating and ranking alerts against the compromised host confirms C2 Beaconing as the dominant alert type — the internal network is compromised, with the external IP acting as the attacker's C2 server.

#### Stage 5 — Data Exfiltration Attempt

```bash
cat firewall.log | grep <compromised_IP> | cut -d' ' -f5,6,7 | uniq | sort
```

Shows the compromised host sending extensive traffic to external IPs on ports 80/8080.

```bash
cat ids_alerts.log | grep <compromised_IP> | tail
```

Confirms via *"ET INFO Possible HTTP POST Large Upload"* alerts, classified as **Potential Data Exfiltration** — direct evidence of data being pushed out of the network.

---

### Investigation Workflow Summary

```
Reconnaissance (port scan) → Initial Access (VPN brute-force) → Lateral Movement (SMB/RDP/SSH exploitation)
    → Command & Control (beaconing) → Data Exfiltration (large HTTP POST uploads)
```

This mirrors the **Cyber Kill Chain** (Section 78) almost exactly — demonstrating how real-world perimeter log correlation reconstructs an attacker's path from first probe to data theft.

> **Note:** Logs this large are often more efficiently investigated in a SIEM platform like **Splunk** (`index=network_logs`) rather than manual command-line filtering — though the underlying analytical logic (filter → pivot → correlate → confirm) remains the same either way.

## Summary

- A network is built from **endpoints, file/database servers, application servers, AD/authentication servers, routers/switches,** and **firewalls**, each with its own security importance — endpoints are the most common entry point, file/database servers are prime ransomware and exfiltration targets, and AD servers are the identity backbone whose compromise can bring down an entire enterprise.
- **Network visibility** ("you can't defend what you can't see") comes from two log categories: **host-centric logs** (OS, application, and security tool logs — what happened *inside a room*) and **network-centric logs** (firewalls, IDS/IPS, routers/switches, web proxies, VPN — *who entered and left the building*), and a complete attack timeline requires correlating both.
- The **network perimeter** — firewalls, routers/gateways, the DMZ, and remote access gateways — is the organization's first line of defense and usually where analysts first see malicious activity such as scanning, brute-force, exploitation of exposed services, and exfiltration channels.
- Pattern recognition drives triage: **one source to many destinations** suggests scanning, **one source to one destination repeatedly** suggests brute-forcing, **perfectly regular intervals** suggest malware beaconing, and an **IDS alert that explains why it fired** is more valuable than a plain firewall block.
- A worked five-stage investigation using `grep`, `cut`, `sort`, and `uniq -c` on firewall, IDS, and VPN logs reconstructs a full chain — **reconnaissance → VPN brute-force → lateral movement → C2 beaconing → data exfiltration** — mirroring the Cyber Kill Chain, and in practice a SIEM like Splunk handles logs this large more efficiently with the same filter → pivot → correlate → confirm logic.
